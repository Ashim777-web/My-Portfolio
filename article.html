Analyzing a Web Authentication Vulnerability

Mar 12, 2026 · 6 min read Intermediate
Web SecurityBurp SuiteAuthentication
Contents
Context Discovery Exploitation Findings Lessons learned References

Context

This write-up covers a session-handling flaw I found while working through a deliberately vulnerable training application. The goal wasn't to find something novel — it was to practice a repeatable methodology for authentication testing.

Discovery

While reviewing requests in Burp Suite's proxy history, I noticed the session token stayed identical before and after login. That's usually a sign the application isn't regenerating session identifiers on privilege change — a common source of session fixation issues.

burp — proxy history
Cookie: session=8f14e45fceea167a5a36dedd4bea2543
-- after login --
Cookie: session=8f14e45fceea167a5a36dedd4bea2543

Exploitation

To confirm the issue was exploitable and not just cosmetic, I captured a pre-authentication session token, handed it to a second browser session, and then completed login in the original session. The second browser inherited authenticated access without ever submitting credentials.

http
GET /dashboard HTTP/1.1
Cookie: session=8f14e45fceea167a5a36dedd4bea2543

Findings

Session Fixation — Medium Severity

The application does not rotate the session identifier after authentication, allowing an attacker who can set a victim's session token to hijack the session once the victim logs in.

Lessons learned

This was a good reminder to check the boring things first — token behavior around login/logout is an easy, high-value check before moving on to more complex authentication logic. I also learned to always validate a finding with a second browser context rather than assuming from the request history alone.
